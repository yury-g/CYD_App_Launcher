## Current Product Intent

The Pulse dashboard is the first-class app. The app shell, Settings, Pin Scanner,
Origin Story, colors, sounds, and render tools are useful only if they do not
make PulseSensor beat detection worse.

The current user-visible goal is:

- Quick, snappy beat detection.
- Stay locked through small user movement.
- Recover quickly if the Playground detector goes quiet while the waveform still
  looks good.
- Make the firmware's thinking visible on the graph with beat markers.

## What Changed In This Working State

### Beat Detection And Recovery

Problem:

- The waveform could look excellent while BPM/IBI failed to lock or slowly
  degraded.
- Touch re-arm could restart the local counters but still fail to recover
  Playground beat events.
- The current branch had accumulated extra acceptance gates on top of the older
  known-good rule, so a visible beat could be rejected after moving to the
  multi-app shell.

Changes:

- Added `activePulseThreshold`, `detectorThresholdForCurrentRange()`, and
  `retunePulseDetectorThreshold()`.
- Re-arm now retunes PulseSensor Playground's threshold from the current visible
  waveform midpoint, clamped to `180..900`, instead of always using fixed `550`.
- The graph threshold label and dotted threshold marker now show the active
  tuned threshold, not always `PULSE_THRESHOLD`.
- Re-arm now happens sooner:
  - `REARM_NO_BEAT_MS` changed from `2200` to `1600`.
  - `REARM_COOLDOWN_MS` changed from `3500` to `1600`.
- Re-arm still refuses recently clipped rail noise, but it no longer blocks just
  because the waveform range is large.
- Strict accepted beats now use the older simple path:
  `decision.strictAccepted = decision.qualified;`
- Cadence helpers and peak-to-peak helpers remain in the code, but the primary
  path is intentionally less brittle for the current hardware testing problem.
- Lock retention is more forgiving:
  - `LOCK_GRACE_BAD_BEATS` changed from `2` to `4`.
  - `LOCK_HOLD_GRACE_MS` changed from `2200` to `4200`.
- `SIGNAL_MOTION_ARTIFACT_RANGE` changed from `420` to `980` so minor movement
  and broad but still useful waveforms do not immediately zero the acquisition
  path.

Why:

- The old pre-multi-app experience felt faster because plausible Playground beat
  events were trusted after basic BPM/IBI/amplitude/range checks.
- The newer stack was too easy to over-filter: cadence, peak-to-peak score,
  clipping, motion range, and lock grace could combine to reject a good-looking
  waveform.
- Dynamic thresholding on re-arm directly addresses the observed symptom where
  the graph is beautiful but `sawStartOfBeat()` stops firing.

### Beat Markers On The Waveform

Problem:

- The user could not tell whether the firmware stopped detecting beats or was
  detecting candidate beats and then rejecting them.

Changes:

- Waveform markers now distinguish detection from acceptance:
  - Large filled white dots: accepted beat that updates BPM/IBI.
  - Smaller hollow white dots: PulseSensor Playground fired
    `sawStartOfBeat()`, but this app rejected/filtered it.
- Marker drawing stores per-marker radius and filled/outline state.
- Markers are redrawn on top of the moving waveform so they remain visible.

Why:

- If dots stop entirely while the waveform is good, the Playground detector or
  threshold is stuck.
- If hollow dots continue but large dots stop, the app qualification logic is
  filtering too aggressively.

### Heart Animation

Problem:

- The current heart had a weird flicker during animation.
- The user wanted the pre-multi-app heart animation effect back, with a white
  outline.

Changes:

- Kept the sprite-backed draw path to prevent flicker.
- Restored the pre-multi-app heart geometry:
  tighter lobes and taller point.
- Kept the red heart fill with a white outline.

Why:

- The old shape felt better to the user.
- Drawing through a small sprite avoids clearing and redrawing directly into the
  header every frame.

### Pin Scanner Crash And Flicker

Problem:

- Tapping `IO35` in the Pin Scanner previously scanned briefly, crashed, and
  restarted.
- Later, the crash was fixed but the scanner had distracting flicker.

Changes:

- The scanner now owns ADC only while actively scanning an ADC-capable selected
  pin.
- PulseSensor Playground is paused while the scanner owns ADC and resumed when
  leaving scanner ownership.
- Scanner redraw is row-local after the initial full redraw or selected-pin
  change.

Why:

- GPIO35 is both the PulseSensor input and a scanner candidate. Letting both
  paths fight over ADC state caused instability.
- Full redraws in the scanner caused visible flicker.

### Color And UI State

The user decided to keep the current color direction after palette exploration.

Current conventions to preserve:

- Acquisition/searching: yellow screen accents and rear RGB LED.
- Locked/real reading: selective light green.
- Text and labels: white across the app, including top nav, title/header, BPM
  number, IBI number, and most Settings text.
- Settings values/adjustable variables: yellow where useful; avoid too much
  green in Settings.
- Nav buttons: white outline in this color scheme.
- Graph paper/grid behind waveform: grey, solid, thin lines.
- Threshold dotted line: white, heavier than the grid.
- Moving waveform line: thicker than the earliest app-shell versions.
- No light blue in the main palette except if deliberately reintroduced for a
  very specific marker experiment. Current beat markers are white.

## Known Risks And Next Test

The latest firmware is intentionally more permissive than `0.4.24` era
signal-core experiments. That is deliberate for restoring the older snappy
feel, but it needs a real body-position test.

Next recommended test:

1. Put the PulseSensor in the same body position used when the user saw the nice
   waveform but no beat detection.
2. Watch dots:
   - No dots: Playground detector/threshold is stuck.
   - Hollow dots: app logic is filtering.
   - Filled dots: BPM/IBI accepted.
3. Watch serial:
   - `accept=strict` means the simple qualified path accepted the beat.
   - `drop=alive signal without beat event` means the detector went quiet and
     auto re-arm fired.
   - `clip=100` or repeated `signal=0`/`signal=1023` means electrical/contact
     railing, not a UI problem.
4. If behavior still degrades with a good waveform, capture raw diagnostics with
   `cyd_diag` and analyze with the existing tools.

Diagnostic workflow:

```bash
python3 -m platformio run -e cyd_diag -t upload --upload-port /dev/cu.usbserial-10
python3 tools/capture_signal_log.py --port /dev/cu.usbserial-10 --seconds 60
python3 tools/analyze_signal_log.py logs/<capture>.csv
```

## Rules For The Next Model

- Keep `readPulseSensor()` first in `loop()`.
- Do not add decorative UI work that can block the 500 Hz signal path.
- Avoid full-screen redraws during live pulse acquisition.
- Do not use GPIO21/GPIO22 as trusted PulseSensor analog inputs on this CYD.
  GPIO35 is current dashboard input; GPIO27 is the other promising ADC candidate.
- Keep Pin Scanner ADC ownership separate from PulseSensor ownership.
- Do not remove the beat marker distinction until the detection-vs-filtering
  question is resolved.
- If the waveform looks good but there are no markers, focus on Playground
  threshold/re-arm state.
- If markers are hollow but not filled, focus on qualification filters.
- Treat `docs/signal-first-architecture.md`, `docs/signal-behavior-log.md`, and
  this handoff as required context before changing beat math.
